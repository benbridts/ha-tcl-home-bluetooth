# BLE connection management via HA bluetooth utilities (v2)

The integration now uses Home Assistant's full BLE connection stack: `async_ble_device_from_address` for device lookup, `establish_connection` for managed connection with retry and slot management, `asyncio.Lock` for connection serialization, a disconnect callback for unexpected disconnections, and a single retry in `_send_command`. The manual retry constants (`MAX_CONNECT_ATTEMPTS`, `CONNECT_RETRY_DELAY`) and the `_connected` flag are removed. `protocol.py` gets a minor cleanup moving `CMD_GET_VERSION` to module-level imports.

All three issues from the v1 review (race in `_ensure_connected`, incomplete HA BLE adoption, no retry on send) have been addressed.

**Watch for:** Disconnect callback doesn't update entity state to unavailable — a disconnected device will still show its last-known power/source/volume until the next command attempt fails and `_ensure_connected` sets `_attr_state = None` (likely). The `call_soon_threadsafe` in `_handle_disconnect` is unnecessary since HA's `establish_connection` dispatches the callback on the event loop already (confirmed).

**Verdict**: APPROVED

## High-level view

The connection lifecycle is now fully managed by HA's bluetooth infrastructure. `establish_connection` handles retry with backoff and adapter slot allocation internally, so the manual retry loop disappears cleanly. The `asyncio.Lock` remains to serialize `_ensure_connected` calls from concurrent entity commands (volume + source arriving simultaneously), with a double-check-locking pattern that avoids holding the lock when already connected.

The disconnect callback (`_handle_disconnect`) clears internal client state but doesn't mark the entity as unavailable. This means HA's UI will display stale state (last-known volume, source, power) until the next command attempt triggers a reconnection failure path. Whether this is intentional "optimistic last-known" behavior or an oversight depends on the desired UX.

## Disconnect handler and entity availability

The `_handle_disconnect` callback nulls `_client`, `_write_characteristic`, and `_notify_characteristic` but doesn't touch `_attr_state`:

```python
def _handle_disconnect(self) -> None:
    _LOGGER.warning("Device %s disconnected unexpectedly", self._address)
    self._client = None
    self._write_characteristic = None
    self._notify_characteristic = None
    self.hass.loop.call_soon_threadsafe(self.async_write_ha_state)
```

Compare with the failure path in `_ensure_connected`:

```python
except (BleakError, TimeoutError, OSError) as err:
    self._client = None
    self._attr_state = None          # <-- marks entity unavailable
    self.async_write_ha_state()
```

The asymmetry means: if the device goes away and the user isn't actively sending commands, the UI stays frozen at the last-known state indefinitely. A user watching the dashboard won't know the device disconnected until they try to interact with it.

The `call_soon_threadsafe` usage is also misleading: since HA's `establish_connection` dispatches the disconnect callback on the event loop, `self.async_write_ha_state()` can be called directly. Using `call_soon_threadsafe` from the event loop works (schedules for the next iteration) but signals to future readers that this callback runs on a foreign thread, which is incorrect.
