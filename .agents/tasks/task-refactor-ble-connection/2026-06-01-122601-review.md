# BLE connection management refactored to HA bluetooth utilities

The integration's connection lifecycle moves from a hand-rolled retry loop with `asyncio.Lock` to Home Assistant's `async_ble_device_from_address` for device lookup, while still using raw `BleakClient` for the actual connection. The manual `MAX_CONNECT_ATTEMPTS` / `CONNECT_RETRY_DELAY` constants, the `_connected` flag, and the reconnect-on-send-failure logic are all removed. A minor cleanup in `protocol.py` promotes the `CMD_GET_VERSION` import from a local scope to module level.

**Watch for:** The refactoring removes all retry and concurrency protection but does not replace them with HA's `establish_connection` helper that provides those guarantees (confirmed). The result is a simpler flow that is also more fragile under transient BLE failures.

## High-level view

The connection strategy shifts from "retry 3 times with backoff, serialize via lock" to "look up the device in HA's bluetooth manager, attempt one connection, fail immediately on error." This removes the concurrency guard entirely — two simultaneous `_send_command` calls can now race through `_ensure_connected` and both try to create a new `BleakClient`.

The `_send_command` path goes from "send, and if it fails reconnect and retry once" to "send, and if it fails null the client and return False." Commands that fail transiently will now surface as errors to the user rather than self-healing.

## Connection concurrency after lock removal

The old code held `self._connect_lock` around the entire connect sequence, so concurrent `async_turn_on` + `async_set_volume_level` calls would serialize. The new `_ensure_connected` has no serialization:

```python
if self._client and self._client.is_connected:
    return True

# Two callers can both pass the above check when _client is None
self._client = BleakClient(ble_device)
await self._client.connect()
```

If two coroutines call `_ensure_connected` at the same moment (both see `self._client is None`), each will create its own `BleakClient` and attempt to connect. The second assignment to `self._client` overwrites the first, leaking a connected-but-unreferenced BleakClient that never gets disconnected.

## No reconnect on send failure

The old `_send_command` caught write failures and attempted one reconnect-then-resend cycle. The new version:

```python
except (BleakError, TimeoutError, OSError) as err:
    _LOGGER.error("Failed to send command: %s", err)
    self._client = None
    return False
```

This nulls the client so the *next* command will reconnect, but the *current* command is lost. For power-toggle this means a missed toggle that the user perceives as unresponsiveness. The fail-fast approach is defensible for a custom component, but it's a regression in reliability from the previous behavior.

## Incomplete adoption of HA's BLE connection pattern

The feature description mentions `establish_connection` as the target pattern, and `async_ble_device_from_address` is indeed used, but the actual connection is still a bare `BleakClient(ble_device)` / `await self._client.connect()`. The standard HA BLE integration pattern (used by e.g. `switchbot`, `led_ble`) uses `establish_connection` from `homeassistant.components.bluetooth` which:

- Manages connection slots (BLE adapters have limited concurrent connections)
- Provides automatic retry with backoff
- Registers a disconnect callback
- Serializes connection attempts to the same device

Without it, the refactoring is half-migrated: it uses HA's device lookup but bypasses HA's connection lifecycle management. The code is simpler than before, but doesn't gain the reliability benefits that motivated the refactoring.
